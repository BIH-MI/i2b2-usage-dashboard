# i2b2-usage-dashboard

## About the project

This interactive dashboard analyzes usage metrics to provide data stewards and administrators with a comprehensive understanding of how users at their institution are interacting with the Informatics for Integrating Biology and the Bedside (i2b2) platform. This can help to identify strengths and limitations of the platform in general, as well as the current data representation supporting the local use case. It can thus serve as a communication aid for the dialog with users to identify potential areas for improvement in supporting efficient access to health data.

It reads the query history and user data directly from the i2b2 Postgres database.

It consists of a React frontend (built with Vite, in `react-dashboard/`) and a FastAPI backend (in `backend/`). Both run as Docker containers.

This version is a rewrite of the earlier Dash application. The previous version is available as release [v1.0.0](../../releases/tag/v1.0.0).

## Features

- Queries, users, sessions and registrations over time, with an activity calendar
- Most used concepts, query complexity, durations and statuses
- A detail page for every query with its structure, constraints and timing
- A user filter and group exclusion that apply to all pages
- Login with user roles, user management and password change
- A pseudonymized view for screen sharing and PNG downloads

## Requirements

- Docker with Docker Compose 2.24 or newer
- For deployment: an i2b2 installation with a Postgres database
- For the tests and the demo data generator: Python 3.12

## Quick demo (no i2b2 needed)

To try the dashboard without an i2b2 installation, start it with synthetic demo data:

```bash
docker compose -f docker-compose.yml -f docker-compose.demo.yml up -d --build
```

Then open http://localhost:5174 and log in as `demo` / `demo1234`.

The demo runs a small Postgres database (`demo-db`) containing only the i2b2 tables the dashboard reads, populated with synthetic users, sessions and queries covering the last 18 months. **All data is synthetic and serves only to illustrate the visualizations;** a banner in the dashboard indicates this. The demo requires no `.env` file. It creates a random session secret on the first start, and it uses its own containers, volumes and network, so it does not affect an existing setup.

The data is generated by `demo/generate_seed.py`, which writes `demo/seed.sql` and the demo login `demo/users.json`. The dates are relative to the moment the demo database is created, so the demo always shows recent activity. To regenerate and restart (needs Python with the `bcrypt` package):

```bash
python demo/generate_seed.py
docker compose -f docker-compose.yml -f docker-compose.demo.yml down -v
docker compose -f docker-compose.yml -f docker-compose.demo.yml up -d --build
```

The demo database is also reachable on `localhost:5433`, for example for the [tests](#tests).

## Deployment

The dashboard connects to an existing i2b2 database. `docker-compose.yml` starts only the dashboard's own two containers, `backend` and `frontend`.

The dashboard requires a login. Two things are not in the repository and must be created once on every machine: the secret that signs the login sessions, and the first admin account. Follow the steps below in order.

### 1. Configure

```bash
cp .env.example .env
```

Fill in the database connection in `.env` (see [Environment](#environment)). `.env` is ignored by git.

The database user needs read access to the data (CRC) schema and the PM schema of i2b2. The database host must be reachable from inside the backend container.

### 2. Create the session secret

Run this in the project root (where `docker-compose.yml` is), before starting the containers:

```bash
mkdir secrets
python3 -c "import secrets; open('secrets/jwt_secret.txt','w').write(secrets.token_urlsafe(48))"
chmod 600 secrets/jwt_secret.txt
```

`secrets/` is ignored by git. Create a new secret on each machine; do not copy it from another one. Without this file, the backend stops at startup with `Missing secret file: jwt_secret`.

On Windows, use `python` instead of `python3` and skip the `chmod` line.

### 3. Start the containers

```bash
docker compose up -d --build
```

The dashboard is then available at http://localhost:5174. On a server, serve it over HTTPS, for example behind a reverse proxy: the login cookie is only sent over HTTPS, with `localhost` as the only exception.

### 4. Create the first admin

```bash
docker compose run --rm backend python create_user.py
docker compose restart backend
```

The script asks for a username, a role, and a password. Enter `admin` as the role. The password needs at least 8 characters. The restart makes the running backend load the new account.

### 5. Add further users

Log in to the dashboard as the admin, open the account menu in the top-right corner, and choose **Settings**. Users added there can log in immediately.

- Roles: `admin` can manage users, `user` can only view the dashboard.
- Passwords need at least 8 characters.
- An admin cannot delete or demote their own account, so there is always at least one admin.

### Where the login data is stored

- `secrets/jwt_secret.txt` - signs the login sessions. Replacing it logs everyone out.
- Docker volume `dashboard-data` (`/data/users.json` in the backend container) - usernames, roles, and bcrypt password hashes. Plain passwords are never stored.

`docker compose down -v` deletes this volume.

### Running behind a proxy under a sub path

If the dashboard is served under a path like `https://example.org/usage/`, set `VITE_BASE_PATH=/usage/` in `.env` and rebuild the frontend:

```bash
docker compose up -d --build frontend
```

### Environment

Settings in `.env` (see `.env.example`):

- `DB_HOST` - hostname of the i2b2 Postgres server. Required.
- `PORT_DB` - Postgres port. Required.
- `DB_NAME` - database name. Required.
- `DB_USER` - Postgres user the backend connects as. Required.
- `I2B2_PG_PASS` - password of that user. Required.
- `I2B2_DATA_SCHEMA` - schema with the query history tables (`qt_query_*`). Defaults to `i2b2demodata`. Change it if your i2b2 installation uses another data schema.
- `I2B2_PM_SCHEMA` - schema with users, logins and sessions (`pm_*`). Defaults to `i2b2pm`.
- `VITE_BASE_PATH` - URL path the dashboard is served under. Defaults to `/`.
- `INSTANCE_NUM` - suffix for the container names. Defaults to `01`.

## Tests

Unit tests run without a database. Integration tests run the real SQL against a Postgres database with the i2b2 tables. They read the connection from the environment or from `.env`: `INTEGRATION_DB_HOST`, `INTEGRATION_DB_PORT`, `INTEGRATION_DB_USER`, `INTEGRATION_DB_NAME` and `I2B2_PG_PASS`. Without these settings, the integration tests are skipped. For the synthetic demo database, start the demo first and use `localhost`, port `5433`, user `demo` and database `i2b2`. From the `backend` folder:

```bash
pip install -r requirements-dev.txt
pytest                                                          # unit tests
pytest tests/integration                                        # integration tests
```

## Using the dashboard

- **Charts:** every chart has an info icon (i) in its top-right corner. Hover over it to see what the chart shows. The download icon next to it saves the chart as a PNG image.
- **Date range:** pick a start and end date, or use the shortcuts (Last Month to Last 2 Years, All Time). All charts follow the selected range, also when switching pages.
- **All users by default:** without a selection, every chart includes all users. The line under the page title shows whether all users or a selection is shown.
- **User filter:** "Select Users" in the sidebar limits all charts to the chosen users. The "Exclude" chips below it remove everyone in a group: from the selected users, or from all users if none are selected. "Reset" removes only the group exclusions and keeps the selection (see [Setting up user groups](#setting-up-user-groups)).
- **Per-user charts:** "Show" sets how many users are displayed at a time, most active first. Type a number or pick one from the list, and use Prev/Next to page through the rest. Without a selection, these charts include every user with queries in the selected range.
- **Clickable charts:** in most charts, every point, bar and calendar day can be clicked. Where a point stands for a single query (the scatter plots on the Queries page), the click opens that query's detail page. Otherwise it opens the list of queries behind that point, and each query in the list links to its detail page. In "Login Attempts by Status", a click lists the login attempts with that status instead.
- **Query search:** "Select Query" in the sidebar opens a query directly by its ID.
- **Account menu:** your name in the top-right corner. It contains **Change password**, **Log out** and, for admins, **Settings**.
- **Change password:** every user can change their own password. The current password is asked again, and the new one needs at least 8 characters.
- **Settings (admins only):** add users, change a user's role between `admin` and `user`, and delete users. Admins cannot change their own role or delete their own account.
- **Display settings** at the bottom of the sidebar, saved in the browser:
  - **Date format:** switches between `DD.MM.YYYY` and `MM/DD/YYYY`, for the date picker and for all dates and times in lists.
  - **Usernames hidden:** shows `User 1`, `User 2`, ... instead of the usernames on every page and in downloaded PNGs, for example for screen sharing. Each user keeps the same alias on every page. This only changes what is displayed: the real usernames are still sent to the browser, so it does not restrict access.
  - **Light/dark mode.**

## Setting up user groups

The "exclude groups" panel requires group data. It must be added manually in the i2b2 webclient:

1. Log in to the i2b2 webclient as an admin.
2. Open the Admin Dashboard, navigate to Users, and edit a user.
3. Under parameters, add a new parameter named `group`. The value is the group name and can be any string.
4. Use the same value for every user belonging to the same group.
